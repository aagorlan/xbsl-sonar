# xbsl-sonar

Проверки **безопасности и производительности** кода XBSL (1С:Предприятие.Элемент):
то, чего не ловит сборка. Синтаксис здесь не проверяется — это делает сама платформа.

- Разбор XBSL — движок [keyfire/xbsl](https://github.com/keyfire/xbsl) (MIT), закреплённой
  версией; его собственные правила в анализе не участвуют, работают только правила отсюда.
- Свод проверок — ISO/IEC 5055 (CISQ: безопасность и эффективность) и OWASP Top 10 2021;
  у каждой проверки код `ПР-NN` и пункт CWE.
- Работает **сам по себе** (находки в консоли и файлом, код возврата для CI) и **с SonarQube**
  через плагин [sonar-bsl-plugin-community](https://github.com/1c-syntax/sonar-bsl-plugin-community).

## Происхождение

Проверки написаны в ходе разработки социальной сети для профессионалов
[«Профессионалы»](https://allhands.pro) на 1С:Предприятие.Элемент. Каждая новая проверка входила
в работу вместе с очередной задачей сети и проходила ворот: **ноль ложных находок** на коде сети
и на демонстрационных приложениях и библиотеках 1С:Элемент. Находки на коде сети исправлялись
или становились пунктами технического долга с пометкой исключения — анализ стоит в проверке
каждого изменения сети.

## На чужом коде

Анализатор находит проблемы не только в коде, под который его писали. Прогон версии 0.30.0
по демонстрационным приложениям и библиотекам 1С:Элемент (выгрузка 2026 года, 924 модуля XBSL,
58 тысяч строк) — без подсказок ПР-21 и намеренно открытых точек ПР-03:

| Группа | Находок | По проверкам |
|---|---|---|
| безопасность | 44 | ПР-01 — 5, ПР-02 — 1, ПР-04 — 1, ПР-05 — 4, ПР-07 — 2, ПР-08 — 5, ПР-09 — 7, ПР-10 — 2, ПР-12 — 4, ПР-22 — 6, ПР-26 — 6, ПР-27 — 1 |
| производительность | 88 | ПР-14 — 16, ПР-16 — 1, ПР-17 — 59, ПР-19 — 1, ПР-25 — 11 |

Каждая находка разобрана по коду. Ложные, которые нашлись при разборе, закрыты правкой правил
в общем виде — условием языка, без привязки к разобранному коду; две оставшиеся общим условием
от настоящих не отличить, ещё три зависят от намерений автора. Места находок здесь
не приводятся.

## Данные о языке

Движку нужны ключевые слова XBSL. Их автор извлекает из дистрибутива платформы;
здесь они **встроены** — перечень слов языка в `xbsl_sonar/keywords.py`, — и ничего,
кроме кода проекта, для запуска не нужно. Текста справки в репозитории нет.

Если платформа добавила ключевое слово раньше, чем вышла новая версия xbsl-sonar,
передайте выгрузку справки 1С:Элемент из своего проекта: `--help-dir <каталог с topics/>`
(нужна страница `topics/keywords/index.md`) — таблица прочитается из неё.

## Самостоятельный запуск (без SonarQube)

Нужен Python 3.10+.

```sh
python3 -m venv .venv
.venv/bin/pip install "xbsl-sonar @ git+https://github.com/aagorlan/xbsl-sonar@v0.31.0"

.venv/bin/xbsl-sonar check <каталог проекта> --json находки.json
```

После `check` укажите один или несколько каталогов исходников. Анализатор
обходит выбранные каталоги рекурсивно. Например, если приложение и библиотеки
лежат в соседних каталогах:

```sh
xbsl-sonar check ./исходники
xbsl-sonar check ./исходники/приложение
xbsl-sonar check ./исходники/библиотека
xbsl-sonar check ./исходники/приложение ./исходники/библиотека
```

Первый запуск охватывает все исходники под общим каталогом. Второй и третий
выбирают приложение или библиотеку. Последний выбирает два конкретных каталога.
Если библиотека вложена в каталог приложения, рекурсивный обход включит её.
Выбор каталога задаёт файлы для диагностики. Отдельные правила могут читать
соседние файлы или метаданные проекта, чтобы восстановить контекст.

Что получается:

- в консоли — находки в виде `файл:строка:столбец: [ПР-NN] сообщение` и итог;
- `--json` — те же находки файлом: правило, место, сообщение, исключение;
- **код возврата**: `0` — находок без исключения нет (подсказки — правила уровня `INFO`, ПР-21, — не в счёт), `1` — есть, `2` — ошибка запуска.
  Этого достаточно, чтобы ронять проверку в любом CI.

Полезное:

- `--rules ПР-01,ПР-15` — только перечисленные правила;
- `--help-dir <справка>` — ключевые слова из выгрузки справки, а не встроенные
  (см. «Данные о языке»);
- `xbsl-sonar data --out <каталог>` — собрать данные о языке один раз
  и дальше запускать `check --data-dir <каталог>`.

### Периметр (ПР-03)

Точка без аутентификации — не ошибка, а решение: её открывают намеренно. Поэтому находка
ПР-03 закрывается не исключением с долгом, а записью в **перечне периметра** — текстовом
файле проекта, который передаётся параметром `--perimeter`:

```text
# путь: Ключ — почему открыто
IT/Проект/Гость/Лендинг.yaml: РежимАутентификации — лендинг для гостей
IT/Проект/Обмен/Сервис.yaml: Вызов — приём сообщений, секрет в адресе
```

Запись закрывает все находки с этим ключом в этом файле. В коде XBSL точку можно отметить
и на месте — `// анализ:периметр — причина` в строке находки или строкой выше. Новая точка
без записи роняет проверку: открыть периметр незаметно для проверяющего PR нельзя.

### Персональные данные (ПР-07)

Что в конфигурации персональные данные и каким методом пишется журнал доступа к ним, знает
только проект — поэтому эта часть ПР-07 настраивается:

```sh
xbsl-sonar check IT \
    --pd-entities УчастникиПерсДанные \
    --pd-journal ЖурналДоступаПДн.ЗафиксироватьДоступПДн \
    --incident-sinks ОбращениеВПоддержку.ЗарегистрироватьОшибку
```

- `--pd-entities` — сущности ПДн через запятую; измерения (ключ записи) правило берёт
  из их YAML и чтение одних измерений находкой не считает. **Без перечня чтение ПДн
  не проверяется** — об этом строка в выводе; проверка исключений и обращений работает всегда.
- `--pd-journal` — метод журнала доступа; не задан — любое чтение ПДн с клиента без сверки
  с текущим пользователем находка: журнала нет.
- `--incident-sinks` — методы, которые пишут обращения в поддержку или в другой журнал,
  который читают люди; текст исключения проверяется и без них.

### Согласованные находки (ПР-02, ПР-04, ПР-05, ПР-07, ПР-16, ПР-17)

Разметка, которую правило не может проверить до конца (экранирование в другом модуле,
число из своего сервиса), известный опрос сервера таймером, выражение формы, которое
ходит на сервер, поле администратора без проверки при записи и повышение прав
без сверки, которое делает только безопасное, — если их переделку
отложили, — закрываются записью в **перечне согласованных находок**
(`--agreed`), а не исключением с долгом: пометку в YAML не поставить — комментариев там нет.

```text
# путь: ПР-04 Ключ — почему безопасно
IT/Проект/Чат/Окно.yaml: ПР-04 КонтейнерHtml Переписка — параметры экранируют «<» при подстановке
IT/Проект/Лента/Форма.xbsl: ПР-16 Таймер ОбновитьСчётчики — опрос раз в 10 с, переделка в ТД-7
```

Ключ — начало сообщения находки до двоеточия. Причина обязательна.

### Исключения

Находку, которую решено не исправлять, отмечают в коде — в строке находки или строкой выше:

```xbsl
// анализ:исключение ПР-15 ТД-12 — разовая обработка десятка записей
знч Настройки = Запрос{...}.Выполнить()
```

После кода правила — ссылка на запись, где решение обосновано (например, пункт
технического долга), после тире — причина. Находка под пометкой не роняет проверку,
но остаётся в отчёте с этой ссылкой. Пометка для другого правила не действует.

## Запуск с SonarQube

Сервер разворачивается по [техническому заданию](docs/развёртывание.md): SonarQube
Community Build, плагин веток и плагин 1С с описаниями правил отсюда.

### В GitHub Actions

Готовый процесс — `.github/workflows/analysis.yml`, вызывается из вашего репозитория:

```yaml
name: Анализ кода
on:
  pull_request:
  workflow_dispatch:
jobs:
  analysis:
    uses: aagorlan/xbsl-sonar/.github/workflows/analysis.yml@v0.31.0
    with:
      version: v0.31.0
      paths: src
      perimeter: docs/периметр.txt         # перечень для ПР-03; можно не задавать
      pd-entities: УчастникиПерсДанные     # для ПР-07; можно не задавать
      pd-journal: ЖурналДоступаПДн.ЗафиксироватьДоступПДн
      incident-sinks: ОбращениеВПоддержку.ЗарегистрироватьОшибку
      sonar-url: ${{ vars.SONAR_URL }}      # пусто — без SonarQube
      runs-on: ubuntu-latest               # или self-hosted
    secrets:
      sonar-token: ${{ secrets.SONAR_TOKEN }}
```

Процесс ставит xbsl-sonar, проверяет код, пишет находки в сводку запуска, отправляет
отчёт в SonarQube (для PR — как анализ PR, иначе — как анализ ветки) и краснеет,
если есть находка без пометки исключения. Сканер SonarQube скачивается со встроенной
Java — ставить её на исполнитель не нужно. На своём исполнителе нужны Python 3.10+
с модулем `venv`, `curl` и `unzip`.

### Руками

Рядом с кодом — `sonar-project.properties`:

```properties
sonar.projectKey=<ключ проекта в SonarQube>
sonar.sources=<каталог проекта>
sonar.sourceEncoding=UTF-8
# Файлы XBSL отдаются плагину 1С
sonar.bsl.file.suffixes=.xbsl
```

Затем:

```sh
xbsl-sonar check <каталог проекта> --bsl-report .xbsl-sonar/bsl-report.json
sonar-scanner \
  -Dsonar.host.url=<адрес SonarQube> \
  -Dsonar.token=<токен анализа> \
  -Dsonar.branch.name=<ветка> \
  -Dsonar.bsl.languageserver.enabled=false \
  -Dsonar.bsl.languageserver.reportPaths=.xbsl-sonar/bsl-report.json \
  -Dsonar.bsl.universal.createExternalIssues=true
```

- `languageserver.enabled=false` — встроенный анализатор BSL выключен: он рассчитан
  на язык 1С:Предприятия 8 и XBSL не разбирает;
- отчёт `--bsl-report` — в формате BSL Language Server, находки в нём с `source: universal-rules`
  и кодом правила `PR-NN` (латиницей — ключ правила на сервере);
- `universal.createExternalIssues=true` — находка правила, которого сервер ещё не знает
  (описания не обновлены), всё равно появится как внешняя.

### Описания правил на сервере

```sh
xbsl-sonar rules-file --out universal.json
```

Файл кладётся на сервер, путь к нему — в настройку сервера
`sonar.bsl.universal.rulesPaths`, и сервер перезапускается: плагин читает описания
при старте. Делать это при каждой новой версии xbsl-sonar, где появились проверки.
Правила с описанием плагин сам собирает во встроенный профиль качества
«Universal - full check» — его и назначить проекту.

## Разработка

```sh
python3 -m venv .venv && .venv/bin/pip install -e '.[dev]'
.venv/bin/python -m pytest
```

При проверке переносимости исходники передают по фактическому пути. Глубина
каталогов, имя корня и наличие манифеста не должны менять результат там, где
правилу достаточно кода. Сначала разбирают подходящие методы в исходниках
вендора и записывают ожидаемые предупреждения, затем сравнивают их с выводом
анализатора. Для ПР-01 эту сверку можно повторить отдельно:

```sh
XBSL_VENDOR_DEMO=/путь/к/e1c .venv/bin/python -m pytest -q tests/test_pr01.py
```

`XBSL_VENDOR_DEMO` указывает на каталог с отдельными приложениями и библиотеками
из выгрузки вендора. Без него выполняются синтетические примеры, в том числе
один исходник на трёх глубинах каталогов без манифеста.

Новая проверка — одно правило в `xbsl_sonar/rules.py` (регистрация `@rule` движка,
описание в `RULES`), положительные и отрицательные примеры в `tests/`, строка в таблице
проверок выше и новая версия: подъём `__version__` в `xbsl_sonar/__init__.py` — метку
`v<версия>` и выпуск на странице Releases после вливания в `main` ставит процесс «Выпуск». Ворот правила: ноль ложных находок на рабочем коде.

### Зеркало на GitFlic

Процесс «Зеркало GitFlic» переносит ветку main, метки и опубликованные выпуски после изменений main и после выпуска на GitHub. Для первого запуска создайте пустой проект GitFlic, в GitHub Actions задайте переменную GITFLIC_REPO (владелец/проект) и секреты GITFLIC_LOGIN и GITFLIC_TOKEN с доступом к записи в этот проект и созданию выпусков. Запустите процесс вручную. Он сравнивает идентификаторы коммитов и меток, названия, описания и статус предварительного выпуска. При расхождении завершится ошибкой.
