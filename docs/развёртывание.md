# Техническое задание: сервер SonarQube для анализа XBSL

## 1. Назначение

Сервер принимает отчёты анализа кода XBSL (xbsl-sonar) из CI и показывает результаты:
находки по веткам и pull request'ам, их историю и ход анализа. Пользователи — команда
одного-двух проектов XBSL; просмотр — из интернета, по учётным записям.

Анализ кода делает не сервер, а xbsl-sonar на исполнителе CI. Решение «пропускать ли
pull request» тоже принимает CI по отчёту xbsl-sonar — от доступности сервера оно
не зависит. Интеграция SonarQube с GitHub (комментарии в PR) не требуется.

## 2. Состав и версии

Версии закреплены. Обновлять — **только все вместе и только вслед за плагином веток**:
его версия жёстко привязана к версии SonarQube.

| Компонент | Версия | Откуда |
|---|---|---|
| SonarQube Community Build | 26.5.0.122743 | Docker-образ `sonarqube:26.5.0.122743-community` |
| плагин веток `mc1arke/sonarqube-community-branch-plugin` | 26.5.0 | страница выпуска 26.5.0 на GitHub: jar плагина и `sonarqube-webapp.zip` |
| плагин 1С `1c-syntax/sonar-bsl-plugin-community` | 1.20.0 | страница выпуска v1.20.0 на GitHub: jar плагина; по матрице плагина — SonarQube 25.4+ и Java 21 (Java в образе SonarQube) |
| PostgreSQL | 16 | Docker-образ `postgres:16` |
| описания правил xbsl-sonar | версия xbsl-sonar, которой идёт анализ | `xbsl-sonar rules-file --out universal.json` |

Лицензии: SonarQube и оба плагина — LGPL-3.0, ставятся без изменений.

## 3. Способ развёртывания

Docker Compose, два сервиса: SonarQube и PostgreSQL; данные — в именованных томах.

Образ SonarQube собирается из официального с добавлением плагина веток — так, как это
делает `release.Dockerfile` самого плагина:

- jar плагина веток — в `/opt/sonarqube/extensions/plugins/`;
- содержимое `/opt/sonarqube/web` заменяется содержимым `sonarqube-webapp.zip`;
- переменные окружения
  `SONAR_WEB_JAVAADDITIONALOPTS=-javaagent:/opt/sonarqube/extensions/plugins/<jar плагина веток>=web`
  и `SONAR_CE_JAVAADDITIONALOPTS=-javaagent:/opt/sonarqube/extensions/plugins/<jar плагина веток>=ce`.

Допустимо взять готовый образ `mc1arke/sonarqube-with-community-branch-plugin` той же
версии, если такой тег опубликован; сверить по Docker Hub при развёртывании.

Плагин 1С — jar в `/opt/sonarqube/extensions/plugins/` (в образ или томом).
`universal.json` — на томе, доступном контейнеру на чтение, например
`/opt/sonarqube/extensions/xbsl-sonar/universal.json`; файл обновляется без пересборки образа.

Образец — `docker-compose.yml` в репозитории плагина веток.

## 4. Требования к ВМ

- Linux x86-64, Docker Engine и Docker Compose v2.
- Ресурсы — не ниже требований SonarQube 26.5 к серверу (документация SonarQube Server,
  раздел о требованиях). Ориентир для небольшой команды: 2 vCPU, 4 ГБ ОЗУ свободно
  под SonarQube и PostgreSQL, 20 ГБ диска под тома.
- Параметры ядра для встроенного Elasticsearch — по той же документации; ориентир:
  `vm.max_map_count ≥ 524288`, `fs.file-max ≥ 131072`, лимиты контейнера
  `nofile ≥ 131072`, `nproc ≥ 8192`. Параметры ядра — постоянно (`/etc/sysctl.d/`),
  а не до перезагрузки.

## 5. Сеть и доступ

- **Снаружи** сервер доступен по доменному имени через **HTTPS** — обратный прокси
  (nginx, Caddy или аналог) с действующим сертификатом и автоматическим продлением.
- Порт 9000 контейнера наружу **не открыт** — только прокси.
- Анонимный доступ выключен: `sonar.forceAuthentication=true`.
- Пароль встроенной учётной записи `admin` сменён при первом входе; учётные записи —
  на каждого участника команды, администраторские права — только у владельца.
- Исполнитель CI обращается к серверу **по тому же внешнему адресу**.

## 6. Настройки сервера

В `sonar.properties` или переменными окружения контейнера:

| Настройка | Значение | Зачем |
|---|---|---|
| `sonar.core.serverBaseURL` | внешний адрес (`https://…`) | ссылки в интерфейсе и в сводке CI |
| `sonar.forceAuthentication` | `true` | см. раздел 5 |
| `sonar.bsl.universal.enabled` | `true` | плагин 1С принимает внешние правила |
| `sonar.bsl.universal.rulesPaths` | путь к `universal.json` | описания правил xbsl-sonar |

В интерфейсе:

1. Создать проект (ключ согласовать с владельцем проекта кода).
2. Назначить проекту для языка BSL профиль качества **«Universal - full check»** — его
   собирает плагин 1С из правил `universal.json`.
3. Создать **токен анализа проекта** (Project Analysis Token) и передать владельцу
   проекта кода для секрета CI. В переписке и в коде токен не появляется.

**Обновление описаний правил** — при выходе версии xbsl-sonar с новыми проверками:
положить новый `universal.json` на место старого и перезапустить контейнер SonarQube
(плагин читает описания только при старте). Порядок записать в эксплуатационную памятку
сервера.

## 7. Исполнитель CI

Если анализ идёт на своём исполнителе GitHub Actions: Python 3.10+ с модулем `venv`,
`curl`, `unzip`, доступ к github.com и к `binaries.sonarsource.com` (оттуда процесс
скачивает сканер со встроенной Java). Ставить Java на исполнитель не нужно.

## 8. Резервное копирование

Ежедневная копия тома PostgreSQL (`pg_dump`) с хранением не меньше 7 дней. Тома
SonarQube (`data`, `extensions`) восстанавливаются из образа и `universal.json`
и копирования не требуют.

## 9. Приёмка

1. Интерфейс открывается по внешнему адресу по HTTPS; без входа — только страница входа.
2. «Администрирование → Marketplace → Installed»: плагин веток 26.5.0 и плагин 1С 1.20.0.
3. «Правила», репозиторий «Universal rules»: есть правила из `universal.json` (`PR-15`).
4. Проект создан, профиль «Universal - full check» назначен, токен анализа выдан.
5. Пробный анализ из CI проходит; в проекте видна ветка, отличная от основной, —
   плагин веток работает.
6. После перезапуска контейнера данные и настройки на месте.

## 10. Что передать владельцу проекта кода

- внешний адрес сервера — в переменную CI;
- токен анализа — в секрет CI (вносит владелец);
- ключ проекта;
- памятку: как обновлять `universal.json`, как обновлять версии (раздел 2).
